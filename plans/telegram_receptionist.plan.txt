TELEGRAM RECEPTIONIST PLAN
==========================

Status: v1 implemented, deployed, and acceptance-tested
Date: 2026-08-04


1. GOAL
-------

Create a private Telegram bot that acts as a receptionist for coding agents
running on the existing VPS.

The bot must:

- Accept messages only from my numeric Telegram user ID in a private chat.
- Work across every repository under `/home/receptionist/repos`, including
  cloning new repositories, without requiring Telegram-side selection.
- Start, resume, inspect, stop, and reset agent conversations.
- Pass ordinary Telegram text to the selected agent as the exact next user
  message, without paraphrasing or adding an application-level prompt.
- Relay useful progress and the final agent response back to Telegram.
- Run the agent and all code operations on the VPS, not on my phone.
- Start with Claude Code, while keeping the orchestration layer adaptable to
  Codex, GitHub Copilot CLI/SDK, and other agents later.
- Run unattended. Agent tool calls should not wait for approval, but broad
  permissions must be contained inside a dedicated Unix account and restricted
  repository root. Production deployment is the exception: an exact immutable
  command requires one explicit Telegram approval before the bot invokes it.

A VPS is a virtual private server: normally a virtual machine hosted by a cloud
provider. It gives us a persistent Linux environment, but being a VM does not by
itself make unrestricted agent commands safe. A process can still access every
file, credential, service, and network resource available to its Unix user.


2. RESEARCH CONCLUSION
----------------------

Recommended first implementation:

  Telegram Bot API
        |
        v
  provider-neutral receptionist service
        |
        v
  Claude Code headless adapter
        |
        v
  selected repository on the VPS

Use Claude Code's programmatic/headless mode for the first adapter:

  claude -p "<exact Telegram message>" \
    --resume "<claude-session-id>" \
    --output-format stream-json \
    --verbose \
    --include-partial-messages \
    --dangerously-skip-permissions

For a new conversation, omit --resume and record the session_id returned in the
JSON result. Run the command with the selected repository as its working
directory. Each Telegram message starts one agent turn; when it completes, the
process exits while Claude's session state remains resumable on disk.

Why this is the best v1:

- It uses Claude Code's real agent loop, tools, skills, hooks, CLAUDE.md files,
  and session context rather than rebuilding those features over the Messages
  API.
- stream-json provides machine-readable lifecycle events, partial output,
  errors, cost metadata, and the resulting session ID.
- --resume turns a sequence of separate subprocess invocations into one
  multi-turn conversation.
- A subprocess boundary makes cancellation, timeouts, logs, and repository
  isolation straightforward.
- The receptionist can define a small provider adapter contract instead of
  depending on Claude-specific Telegram behavior.
- It can use the Claude Code authentication already supported on the VPS. This
  is important because the Claude Agent SDK is intended to use API-key
  authentication for third-party integrations rather than silently reusing a
  personal claude.ai subscription login.

Do not use the direct Anthropic Messages API for v1. It is stateless and would
require us to implement the coding tool loop, command execution, permissions,
conversation persistence, context compaction, and error recovery ourselves.


3. OPTIONS COMPARED
-------------------

A. Existing official Claude Telegram channel

The telegram-channel-forwarder VPS already runs:

- Claude Code in a tmux session.
- telegram@claude-plugins-official.
- A dedicated Telegram bot token and paired allowlist.
- --dangerously-skip-permissions.
- systemd supervision and an independent watchdog bot.
- A UserPromptSubmit receipt hook and restart notification hook.

Advantages:

- Already proven on this VPS.
- Smallest amount of new code.
- Full interactive Claude Code environment, including plugins, hooks, skills,
  memory, and channel reply tooling.
- Official two-way Telegram integration and sender allowlisting.
- Uses a continuously running session, so inbound messages feel immediate.

Disadvantages for the receptionist goal:

- It is Claude-specific.
- One bot is tied to one running Claude process, working directory, and
  continuous context.
- The current deployment cannot truly reset context from Telegram; /clear is
  forwarded as plain text.
- Repository and conversation switching would require supervising multiple
  Claude processes or building a custom channel/router anyway.
- Telegram Bot API messages sent during a restart can be lost because there is
  no history/backfill.
- Channels are still a research-preview feature.

Decision:

Do not extend the existing forwarder bot into the new receptionist. Keep it as
a working reference and fallback. Reuse its operational lessons, but build a
separate bot, service, Unix user, credentials, state store, and repository root.


B. Fresh receptionist around Claude Code headless CLI

Advantages:

- Natural one-message/one-turn request model.
- Exact text can be passed as the next prompt.
- Multiple repositories and sessions are easy to model explicitly.
- Processes can be queued, timed out, cancelled, and restarted independently.
- Provider adapters can hide CLI-specific flags and event formats.
- No long-lived interactive TTY or tmux session is required.
- Claude session IDs survive receptionist restarts.

Disadvantages:

- Some interactive-only behavior is unavailable. In -p mode, terminal UI
  prompts such as multiple-choice questions and plan approval cannot pause for
  input.
- The bot must parse JSON events and decide what progress is useful.
- Each turn pays CLI startup overhead.
- A Claude turn may ask a question in its final text rather than through an
  interactive prompt. That is acceptable: my next Telegram message becomes the
  exact answer and resumes the same session.

Decision:

Use this for v1.


C. Claude Agent SDK

Advantages:

- Official Python and TypeScript libraries around the same Claude Code agent
  loop.
- Native message objects, streaming callbacks, permission callbacks, hooks,
  session resume/forking, and stronger lifecycle control.
- Cleaner than parsing CLI JSON if the product becomes more complex.

Disadvantages:

- Claude-specific.
- Requires API-key/provider authentication for this type of application and
  therefore separate API billing and spend controls.
- It gives less immediate leverage for future CLI providers than a subprocess
  adapter.

Decision:

Keep the receptionist/provider interface compatible with an SDK-backed adapter.
Consider migrating the Claude adapter after v1 if event parsing, interruption,
or session lifecycle becomes brittle.


D. Direct Anthropic Messages API

Advantages:

- Stable HTTP integration and token streaming.
- Full control over prompts and application data.

Disadvantages:

- No Claude Code tool loop, repository agent, shell lifecycle, or session store
  is supplied automatically.
- We would be responsible for safely implementing every tool and repeatedly
  feeding tool results back to the model.
- Least reusable path for running existing coding-agent CLIs.

Decision:

Do not use it for the coding receptionist.


4. FUTURE PROVIDERS
-------------------

Other CLIs are manageable, but they are not interchangeable merely because they
are command-line programs. Each has different session, streaming, permission,
authentication, and cancellation semantics.

Define this internal provider interface:

- start_session(repository, prompt, options) -> event stream + provider session
- resume_session(provider_session_id, prompt, options) -> event stream
- cancel_run(run_id)
- inspect_session(provider_session_id)
- delete_session(provider_session_id)
- healthcheck()
- capabilities() -> streaming, resume, attachments, interruption, cost data

Initial adapters:

1. ClaudeCodeCliAdapter
   - claude -p
   - stream-json parsing
   - --resume session ID
   - --dangerously-skip-permissions

2. Copilot adapter, later
   - Copilot CLI officially supports non-interactive `copilot -p`, silent
     output, --no-ask-user, repository/path grants, and --allow-all/--yolo.
   - The Copilot SDK has explicit persistent session IDs, streaming, working
     directory selection, and resume APIs. The SDK is likely preferable to its
     CLI when we add this provider.

3. Codex adapter, later
   - Perform a focused spike against the installed version and official docs
     before implementation.
   - Do not assume Claude or Copilot flag names, event schemas, or resume
     behavior.

Provider-specific details must stay inside adapters. Telegram handlers should
only know about receptionist sessions, runs, and normalized events.


5. TELEGRAM EXPERIENCE
----------------------

Use a new BotFather bot and long polling. Polling matches the existing VPS
pattern and does not require exposing a public webhook endpoint.

Plain-text behavior:

- If no command is detected, preserve the Telegram message text exactly.
- Do not strip, summarize, quote, or prepend hidden task instructions.
- Associate the message with the currently selected receptionist session.
- If a turn is already running, queue the message and clearly report that it is
  queued. Do not inject it into a running turn in v1.
- The next queued message is submitted only after the prior turn reaches a
  terminal state.

Commands:

- /start        show current provider, repository, and session
- /repos        list repositories currently cloned in the workspace
- /repo         compatibility message explaining that switching is unnecessary
- /new          create a new conversation in the selected repository
- /sessions     list recent conversations for the selected repository
- /switch       switch the active conversation
- /status       show active run, elapsed time, queue depth, and last result
- /stop         terminate the active agent process tree
- /reset        archive the current conversation and create a fresh one
- /provider     show or change the provider for a new conversation
- /verbose      toggle detailed tool/progress messages
- /approve      execute the only pending immutable deployment request
- /deny         permanently reject the only pending deployment request
- /deployments  list recent deployment requests and statuses
- /help         explain commands and exact-message behavior

Each deployment notification also contains Approve and Deny inline buttons tied
to that exact immutable request, so normal use never requires typing an ID.

Output relay:

- Immediately acknowledge receipt with the run ID and selected repository.
- Show compact progress by default: receipt, current high-level activity, elapsed
  time, and then the complete final answer.
- Provide `/verbose` mode for detailed tool/activity events plus VPS system
  state: agent-process RSS, total memory and swap usage, and CPU usage.
- In verbose mode, edit one status message approximately every 30 seconds rather
  than sending a new message for each update.
- Update progress at a conservative interval to avoid Telegram flood limits.
- Send the final response in chunks below Telegram's message-size limit.
- Preserve Markdown/code fences when splitting where practical.
- For very large output, attach a UTF-8 text file and send a short summary.
- Store the complete normalized event log on the VPS even when Telegram receives
  only a compact view.
- Include explicit failure messages for authentication, timeout, process exit,
  malformed event output, missing repository, and session-resume failure.

Attachments are phase 2. The initial release supports exact text messages only.


6. STATE MODEL
--------------

Use SQLite with WAL mode. The bot is single-user initially, but user ownership
must still be present on every row so authorization cannot be forgotten later.

repositories

- id
- name
- absolute_path
- default_branch
- enabled
- created_at

sessions

- id (receptionist-owned UUID)
- telegram_user_id
- repository_id
- provider
- provider_session_id
- display_name
- status: active, archived, broken
- created_at
- updated_at
- last_used_at

runs

- id
- session_id
- exact_prompt
- status: queued, running, succeeded, failed, cancelled, timed_out
- process_id/process_group_id while active
- started_at
- finished_at
- exit_code
- final_response
- error
- provider_usage_json

deployment_requests

- id
- telegram_user_id
- repository_path and immutable Git revision
- exact root command and human-readable summary
- status: pending, approved, executing, succeeded, failed, denied, expired
- created, expiry, notification, approval, start, and finish timestamps
- exit code, bounded output, and error

events

- id
- run_id
- sequence
- provider_event_type
- normalized_event_type
- payload_json
- created_at

bot_state

- telegram_user_id
- active_repository_id
- active_session_id
- verbose

Never store bot tokens, API keys, OAuth credentials, or SSH private keys in
SQLite.


7. AUTHENTICATION AND SECRETS
-----------------------------

Telegram:

- Create a dedicated receptionist bot token.
- Require a private chat.
- Compare update.effective_user.id against one numeric allowlisted user ID
  before command parsing or database access.
- Ignore or explicitly reject all other users, groups, and channels.
- Do not rely on Telegram username or display name; both can change.
- Keep the token and user ID in a server-only environment file with mode 0600.

VPS and agent:

- Create a dedicated `receptionist` Unix user.
- Run the systemd service as that user, never root.
- Clone approved repositories under one root such as
  /home/receptionist/repos.
- Resolve and validate every selected path; it must remain under that root.
- Give the user only the Git credentials it needs.
- Do not copy unrelated forwarder secrets into the receptionist account.
- Do not grant either account a general shell through passwordless sudo. Allow
  only fixed root-owned launchers; the deployment executor additionally
  requires one immutable Telegram-approved request.
- Run Claude with broad permissions only inside this constrained account.
- Redact configured secret environment variables from logs and Telegram output.

This differs deliberately from "root on a VM." It still provides unattended
write/shell/network access within the coding workspace while limiting the blast
radius of a malicious prompt, compromised dependency, or accidental command.


8. PROCESS AND CONCURRENCY MODEL
--------------------------------

- One active run globally for v1 because the current VPS is small and already
  hosts production Telegram services.
- Queue additional messages FIFO.
- Spawn each agent in a new process group.
- Capture stdout and stderr independently.
- Parse stdout line-by-line as provider events.
- Apply a configurable wall-clock timeout, initially 60 minutes.
- /stop sends SIGTERM to the process group, waits a grace period, then SIGKILLs
  that specific process group if necessary.
- On service restart, mark orphaned running rows failed; do not blindly replay a
  possibly completed prompt.
- Persist the provider session ID as soon as it appears.
- Lock each receptionist session so two turns can never mutate the same agent
  context concurrently.
- Add disk, memory, and run-duration limits before allowing parallel agents.

  working-directory control.

11. ACCEPTANCE CRITERIA
-----------------------

- A message from any unauthorized Telegram user cannot start a process, select a
  repository, or reveal state.
- One conversation can inspect and change at least two repositories under the
  workspace root without registration or switching.
- The agent can clone a new repository beneath the workspace root and use it in
  the same conversation.
- Sending "yes", a multiline answer, code, or quoted text results in those exact
  characters being used as the next user prompt, subject only to Telegram's own
  text representation.
- A Claude conversation can be resumed after the bot service restarts.
- /reset creates a genuinely fresh provider session.
- /stop terminates the active process tree without restarting unrelated VPS
  services.
- Two turns cannot execute concurrently in the same conversation.
- Agent output reaches Telegram without exceeding message limits or flooding the
  Bot API.
- Full run events and final responses are auditable on the VPS.
- The agent cannot select paths outside the approved repository root.
- The agent has no root access and cannot read the forwarder's unrelated secrets.
- A failed, timed-out, or cancelled run is visibly reported and never presented
  as success.


12. APPROVED IMPLEMENTATION DECISIONS
-------------------------------------

Approved on 2026-08-04:

- Claude authentication: use a dedicated Claude Code subscription login under
  the new receptionist Unix account.
- Isolation: create a restricted `receptionist` Unix user for the Telegram bot
  and a separate restricted `receptionist-agent` Unix user for Claude, Git, and
  repository writes. This prevents an unrestricted agent turn from reading the
  bot token or bot database through same-user files or `/proc`. Neither account
  has root or general sudo access, and neither can access forwarder secrets.
- VPS repository root: `/home/receptionist/repos`. Do not use the `asce` home or
  account for receptionist files or execution.
- Language: implement v1 in Python.
- Telegram library: use `python-telegram-bot` with Bot API long polling. Do not
  create or maintain a Telethon/MTProto session for this bot.
- Initial repositories (superseded by workspace mode below): approve `www` and create a private
  `sboghani1/agent-sandbox` repository. Add other production repositories only
  after isolation, cancellation, and recovery tests pass.
- Git authority: the agent may push branches. It may propose production
  deployments, but execution requires the explicit one-shot approval described
  in the 2026-08-05 decision log.
- Privileged deployment (superseded on 2026-08-05): v1 initially exposed only a
  root-owned receptionist-specific deployment wrapper. The current broker
  permits the exact displayed root command for any workspace repository only
  after Telegram approval.
- Deployment trigger (superseded on 2026-08-05): the original implementation
  allowed the agent to invoke the receptionist's own deployment automatically.
  All deployments now require one explicit Telegram approval as recorded below.
- Deployment safety: before restart, the wrapper must record the previous
  revision and require the configured tests to pass. After restart it must run a
  health check and automatically roll back to the previous revision if startup
  or health validation fails.
- Concurrency: permit one active agent run globally.
- Run timeout: 60 minutes.
- Queue limit: 10 Telegram messages.
- Telegram input: exact text messages only in v1; no files or photos.
- Progress display: compact by default. `/verbose` adds detailed agent activity
  and edits one resource/status message every 30 seconds with CPU, memory, swap,
  elapsed time, and agent-process RSS.
- Retention: delete detailed events after 30 days while retaining session
  metadata and final responses until explicitly deleted.

Remaining implementation-time inputs:

- The numeric Telegram user ID and new BotFather token, supplied only through
  the VPS secret environment file.
- The exact `www` test command and health-check command required by the
  deployment wrapper once the application exists.
- The eventual production repositories, branches, services, and commands to add
  after v1.


13. IMPLEMENTATION DECISION LOG
-------------------------------

This section records decisions made while implementing the approved design so
the plan remains the source of truth rather than only describing the original
proposal.

QUICK DECISION AND GUARDRAIL INDEX

- Python orchestration instead of Bun:
  `python-telegram-bot`, `asyncio`, subprocess process groups, SQLite, and
  systemd already provide the coordination we need. Bun's shell API would make
  some command syntax shorter, but would not add a missing capability and would
  introduce a second runtime and another dependency/security update surface.
  Current controls enabled by this choice include typed application code, exact
  argv/JSON prompt transport, explicit subprocess timeouts, process-group
  cancellation, systemd watchdog integration, and one shared SQLite state
  machine. Reconsider Bun only if a future JavaScript/TypeScript subsystem has a
  concrete requirement that Python cannot meet cleanly.
- Claude lifecycle:
  one `claude -p` process runs per Telegram turn; provider session IDs preserve
  conversation context between turns. `/stop` terminates the active process
  tree, `/reset` creates a fresh Claude context, a 60-minute timeout bounds
  stalled work, and background Claude tasks are disabled so work cannot outlive
  the observable turn.
- Unix identity separation:
  `receptionist` owns Telegram secrets and bot state; `receptionist-agent` owns
  Claude credentials, Git credentials, repositories, and allowlisted Google
  Sheets credentials. This kernel-enforced boundary prevents agent shell access
  to the Telegram token and unrelated production secrets.
- Workspace freedom with a filesystem boundary:
  the agent may work across or clone any repository beneath
  `/home/receptionist/repos` without Telegram-side switching. Root-owned
  launchers resolve paths and reject execution outside that workspace.
- Exact input and command boundaries:
  Telegram prompts travel as stored text through JSON into one argv element,
  never through shell interpolation. Ordinary agent commands run as the
  unprivileged agent identity.
- Deployment approval:
  the agent has no sudo permission. It writes an immutable request to a narrow
  group-controlled spool; the bot copies it to SQLite and shows its repository,
  revision, summary, and exact root command. Only the authorized user can press
  Approve or use unambiguous `/approve`; requests expire after 15 minutes,
  execute once, and fail if repository HEAD changed after display.
- Resource protection:
  one global agent run, a queue limit of 10, serialized deployment execution,
  bounded command output, subprocess timeouts, and visible CPU/RAM/swap status
  reduce memory pressure and command races on the roughly 1GB shared VPS. The
  receptionist is single-user, but other services also consume this machine's
  memory. If conversations or services crash with kernel OOM kills, repeated
  unexplained process exits, or sustained RAM/swap exhaustion, treat that as a
  capacity limit and move to a larger VPS rather than weakening isolation or
  adding brittle process workarounds.
- Reliability and recovery:
  SQLite WAL persists exact prompts and state; interrupted agent runs and
  deployments are marked failed rather than replayed. systemd watchdog,
  immutable releases, health checks, rollback, daily coherent backups, and
  30-day event pruning keep failures visible and recoverable.
- Telegram authorization and data minimization:
  private-chat plus numeric-user-ID checks run before command handling or
  database access. HTTP client logs are suppressed to avoid token-bearing URLs,
  and only the three required Google Sheets values are exposed to the agent.

2026-08-05 — Separate bot and agent Unix identities

- Decision: run the Telegram service as `receptionist`, but run Claude, Git, and
  repository commands as `receptionist-agent` through a fixed root-owned
  launcher.
- Reason: Claude has broad unattended shell/filesystem authority. If it shared
  the bot's Unix identity, it could read the Telegram token from the environment
  file or `/proc`, regardless of application-level redaction. Unix identity
  separation provides a real kernel-enforced secret boundary.
- Consequence: `receptionist` receives sudo permission only to execute the exact
  agent launcher as `receptionist-agent`; it receives no general shell or root
  sudo. The launcher accepts a JSON request on stdin, validates that the
  repository resolves under `/home/receptionist/repos`, permits only
  `/usr/bin/claude`, and uses `exec` without a shell.

2026-08-05 — Exact prompts use argv/JSON, never shell interpolation

- Decision: Telegram text is stored unchanged in SQLite, encoded in the
  bot-to-agent launcher JSON request, and passed as one `claude -p` argument.
- Reason: this preserves multiline replies and shell metacharacters exactly
  while preventing a Telegram message from becoming shell syntax.
- Verification: automated tests cover multiline text, quotes, code fences, and
  shell-like text such as command substitution characters.

2026-08-05 — Persistent turns use Claude session IDs

- Decision: one Claude subprocess handles one Telegram turn. The receptionist
  captures `session_id` from stream-json events and supplies it with `--resume`
  on the next turn.
- Reason: this provides durable multi-turn context without keeping a fragile
  interactive TTY alive, and allows the bot service to restart independently.
- Consequence: `/reset` archives the receptionist session and creates a new row
  with no provider session ID, guaranteeing a fresh Claude context.

2026-08-05 — Background agent tasks are disabled

- Decision: the root-owned Claude launcher sets
  `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`.
- Reason: `claude -p` terminates lingering background Bash tasks shortly after
  returning its final result. Without this setting, Claude can say it will reply
  when a background command finishes even though the process is about to be
  killed and no later reply is possible.
- Consequence: commands run sequentially inside the current Telegram turn. Long
  work remains observable through the edited status message and is bounded by
  the receptionist's 60-minute timeout.

2026-08-05 — SQLite is the durable queue and audit log

- Decision: persist repositories, user state, sessions, exact prompts, runs,
  normalized events, usage, and final responses in SQLite WAL mode.
- Reason: a memory-only queue would lose exact replies on restart and could not
  safely recover or audit agent activity.
- Recovery behavior: queued runs remain queued; a run marked `running` when the
  process restarts is marked failed rather than replayed, because replaying a
  possibly completed coding turn could duplicate edits, pushes, or deployments.

2026-08-05 — One global worker, bounded queue

- Decision: process one run globally, enforce a 60-minute timeout, and accept at
  most 10 queued messages.
- Reason: the VPS has roughly 1GB RAM and already runs production services.
  Serial execution prevents concurrent agents from exhausting memory or racing
  in the same repositories.
- Capacity assumption: this is a single-user bot on a VPS shared with other
  services. A long Claude turn, dependency installation, test suite, or build
  can still exceed available memory even with serialized agent work.
- Resize trigger: if the kernel reports OOM kills, agent/service processes
  repeatedly disappear without application errors, or RAM and swap remain
  exhausted during normal conversations, upgrade the VPS memory. Do not respond
  by allowing uncontrolled background work, removing the one-run limit, or
  merging the bot and agent identities.
- Cancellation: every agent invocation receives its own process group. `/stop`
  sends SIGTERM through sudo's signal relay, waits 10 seconds, and invokes a
  separate fixed `receptionist-agent` kill helper for SIGKILL if needed.
- Reason for the helper: SIGKILL cannot be caught or relayed by sudo. Killing
  only the sudo monitor could orphan the real Claude process under the agent
  user, invalidating both `/stop` and the 60-minute timeout.

2026-08-05 — Queue worker failures are contained and health-visible

- Decision: catch unexpected exceptions around each run, mark the affected run
  failed, terminate any associated process, notify Telegram when possible, and
  continue servicing the queue.
- Reason: one transient Telegram or parsing exception must not silently kill the
  only worker while the bot continues accepting messages.
- Health behavior: the main heartbeat is withheld if the worker task is dead, so
  deployment health checks fail instead of declaring a bot with a dead queue
  worker healthy.

2026-08-05 — systemd watchdog follows application health

- Decision: run the main service as `Type=notify`, send `READY=1` only after
  Telegram and the worker start, and send `WATCHDOG=1` with each healthy
  heartbeat.
- Reason: `Restart=on-failure` only detects a dead process. It does not detect a
  live event loop whose queue worker has died. Withholding watchdog heartbeats
  makes systemd restart that degraded process automatically.

2026-08-05 — Daily database backups and retention

- Decision: a daily systemd timer uses SQLite's online backup API, keeps
  restricted backups for 14 days, and prunes detailed run events older than 30
  days.
- Reason: copying a live WAL database as ordinary files can produce an
  inconsistent backup. SQLite's backup API produces a coherent snapshot while
  the bot remains online.

2026-08-05 — Replace repository selection with one workspace

- Decision: remove the explicit repository allowlist and make
  `/home/receptionist/repos` the working directory for every new conversation.
- Reason: real tasks commonly span several repositories. Telegram-side
  repository registration and switching add friction without providing a
  meaningful security boundary, because the dedicated agent user already owns
  the workspace and can safely access its children.
- Behavior: `/repos` discovers Git repositories dynamically for information
  only. The agent may inspect existing repositories, clone new ones beneath the
  workspace root, and coordinate cross-repository changes without requesting
  permission to switch.
- Preserved guardrail: path validation still confines the privileged launcher to
  `/home/receptionist/repos`; the agent still cannot read the Telegram bot
  account, forwarder account, or unrelated VPS secrets.

2026-08-05 — Expose only Google Sheets credentials

- Decision: copy only the Google Sheets credential variables and required
  service-account material into an agent-owned secret file, then load those
  allowlisted values in the root-owned Claude launcher.
- Reason: cross-repository work includes updating authorized Google Sheets, but
  exposing the forwarder's complete environment would also disclose unrelated
  Telegram sessions, bot tokens, API credentials, and production secrets.
- Allowed credential scope: `GOOGLE_CREDENTIALS`,
  `GOOGLE_SERVICE_ACCOUNT_JSON`, and `NFL_INTAKE_SHEET_ID`.
- Preserved guardrail: the agent still cannot read the forwarder's `.env`,
  `.env.local`, home directory, or any non-Google credential stored there.

2026-08-05 — One-shot explicit deployment approval broker

- Decision: agents cannot run production deployment commands directly. They
  submit a request containing a repository path, immutable Git revision,
  summary, and exact root command. Telegram displays all four fields and
  execution requires the request's Approve button or an unambiguous bare
  `/approve`.
- Reason: deployment procedures differ across repositories and may require root,
  but a broad reusable sudo grant would let an unattended or prompt-injected
  agent deploy without the user's knowledge. Showing and freezing the exact
  command preserves speed while keeping the user in the authorization path.
- Immutability: the bot copies the agent request into its SQLite database before
  notification. Approval executes that database copy, not the agent-writable
  spool file. The root executor rechecks that repository HEAD still equals the
  displayed revision.
- One-shot behavior: only `pending` requests can be approved; approval is an
  atomic state transition and execution can start once. Denied, expired,
  executing, completed, or failed requests cannot be replayed.
- Expiry: requests expire after 15 minutes so an old Telegram message cannot
  authorize a later, forgotten deployment.
- Scope: any Git repository beneath `/home/receptionist/repos` may propose an
  exact root command. The command itself may update the corresponding
  production checkout and services elsewhere on the VPS.
- Audit and recovery: request status, timestamps, command, exit code, bounded
  output, and error are retained in SQLite. A bot restart marks an interrupted
  deployment failed and never replays it.
- Secret boundary: the agent can write only to a group-controlled incoming
  spool. Only the bot user can approve and invoke the fixed root executor.
- Approval UX: each Telegram request has Approve and Deny buttons whose callback
  contains the immutable UUID. Bare `/approve` and `/deny` are accepted only
  when exactly one request is pending. This avoids typing IDs without guessing
  which request the user intended when several proposals exist.

2026-08-05 — Telegram output is compact and flood-aware

- Decision: acknowledge receipt immediately, edit one status message while
  working, and send the final result in bounded chunks or as a UTF-8 attachment
  when large.
- Reason: forwarding raw token/tool streams would create noise and risk Telegram
  flood limits.
- Verbose behavior: update at most every 30 seconds with agent activity,
  process-tree RSS/CPU, VPS CPU, RAM, and swap. Compact mode updates less often.
- Progress detail: each status edit includes a safe **Current** line derived
  from the latest tool event. File tools show a compact workspace-relative path;
  shell commands and prompts are never echoed because they may contain secrets.
- Update expectation: status edits show **Next update by** in Eastern time,
  calculated as the edit time plus 30 seconds and rounded up to the next minute.

2026-08-05 — Long polling and strict private-chat authorization

- Decision: use `python-telegram-bot` long polling and reject every update unless
  it is a private chat from the configured numeric Telegram user ID.
- Reason: polling requires no public web endpoint and matches existing VPS
  operations. Numeric IDs are stable; usernames and display names are not.
- Bootstrap: discover the initial ID only after the user sends a private
  `/claim <random-one-time-code>` message to the new bot.
- Bot API HTTP-client logging is forced to WARNING. At INFO, the client logs the
  full Telegram request URL, whose path contains the bot token; normal
  operational logs must never persist credential-bearing URLs.

2026-08-05 — Immutable release deployment with detached execution

- Decision: an agent-triggered deployment launches a detached root-owned
  transient systemd unit. That worker validates a clean `main` matching
  `origin/main`, creates an immutable revision-addressed release under
  `/opt/telegram-receptionist/releases`, installs dependencies, runs tests,
  switches a `current` symlink, restarts, and checks a service heartbeat plus
  SQLite integrity.
- Reason: restarting the bot from a deployment process inside the bot's own
  cgroup would kill the deployment before it could validate or roll back.
  Detached transient execution survives the service restart.
- Rollback: retain the previous release symlink and restore it automatically if
  the new service does not become healthy, then health-check the restored
  release before reporting rollback success.
- Notification: deployment status is written atomically to the state directory;
  the bot polls for unseen statuses and reports them after it is available.
- A status is marked seen only after Telegram accepts the notification, so a
  transient send failure remains retryable.
- Build/test failures also write a failed deployment status before cleanup.
- Release pruning explicitly excludes the active `current` target so reusing an
  older revision cannot delete the live release.
- The worker sets its own `umask` and reapplies read/execute permissions to the
  immutable release, so a restrictive caller environment cannot make the
  service's working directory unreadable.
- A failed `systemctl restart` follows the same rollback path as a failed health
  check; shell `set -e` must not bypass rollback before it can restore the prior
  release.

2026-08-05 — Release virtual environments are created at final paths

- Decision: move archived source into its final revision directory before
  creating the virtual environment.
- Reason: Python virtual-environment scripts contain absolute interpreter paths.
  Creating a venv in a temporary directory and moving it would leave broken
  shebangs.

2026-08-05 — Reconcile agent completion separately from Telegram delivery

- Incident: run `8a755e12` completed successfully in Claude and pushed its
  commits, but the receptionist lost the subprocess completion signal after its
  event stream stopped. SQLite continued to show the run as `running`, its
  queued diagnostic message could not proceed, and Telegram never received the
  final response. The Claude process was no longer present and there was no OOM
  evidence.
- Decision: persist agent terminal state and Telegram delivery state
  independently. Runs now retain the last event time, delivery status, attempt
  count, successful chunk cursor, delivery error, and delivered timestamp.
- Dead-process behavior: the worker checks the full process group rather than
  only the original sudo PID. If a recorded process group disappears, it
  reconciles the run from the restricted Claude session reader. A response is
  accepted only when the latest conversation record is a text-only assistant
  response produced after the run began, with no attached tool call. Claude
  task files are retained as diagnostics but are not authoritative because
  completed runs can leave stale pending task records. Recovery never replays
  the prompt.
- Queue safety: a restarted worker will not execute queued prompts while an
  orphaned agent process group is still alive. It waits and reconciles that run
  before returning to the queue.
- Delivery behavior: a completed response is marked pending, sent separately,
  and retried every minute after transient Telegram failures. Multi-message
  responses resume at the first unsent chunk instead of duplicating chunks that
  Telegram already accepted.
- Delivery concurrency: a sender must atomically change the run from pending or
  failed to sending before contacting Telegram. This prevents the run-completion
  path and the one-minute retry poll from delivering the same response
  concurrently. A service restart changes an interrupted sending claim back to
  failed so it can be retried.
- Operator UX: `/recover` and the **Recover worker** button reconcile dead runs,
  retry pending delivery, and restart only a dead queue worker. A live agent is
  not killed or blindly restarted. `/status` shows process and delivery state.
- Startup behavior: the service performs the same reconciliation before
  starting its queue worker, so a bot or VPS restart does not automatically
  label all interrupted runs failed or rerun completed work.
- Fallback boundary: Claude's session JSONL is parsed only by the fixed
  root-owned launcher running as `receptionist-agent`; the Telegram service does
  not gain access to that account's home directory. A receptionist-owned
  append-only output/exit spool remains the preferred future hardening if
  Claude's internal session format changes.
- Deployment requirement: every immutable deployment refreshes the root-owned
  agent launcher from the selected release before restarting the service.
  Updating only the Python package would leave recovery logic split across
  mismatched versions.
- Follow-up incident: run `855d60e4` completed, produced a final assistant
  response, and pushed commit `9d6f7e1`, but the live execution path rejected
  recovery because it still held the pre-start run object whose `started_at`
  was null. The run was reconciled and delivered without replaying its prompt.
- Fix: immediately reload the run from SQLite after `start_run` persists its
  PID and start timestamp. All later recovery comparisons use that durable
  record rather than the stale queued snapshot.
